# FOCUS v0.2 阶段 1：单篇统一入库

Status: ready-for-agent

日期：2026-09-21。范围：阶段 0 已确认决策所界定的阶段 1 单篇 PDF 入库。此状态表示需求可供实施，不表示代码或真实运行验收通过。

## Problem Statement

用户希望先把一篇论文放入知识库，查看可信的原文，并按专题组织它。当前上传流程却把解析、阅读规划和全文阅读准备连成一个任务：即使原文已经成功解析，只要 Plan 或译文未完成，上传仍被报告为失败。用户难以判断文档是否已保存、失败发生在哪一步，以及重试会不会重新上传或丢失已有进展。

同一篇论文也可能属于多个 Topic。用户需要多个专题入口指向同一份来源资产，不能因分类而复制文档、Bundle 或阅读记录。知识库展示、文档入库和专题关联必须有清楚且可恢复的状态。

## Solution

独立网页版提供最小单篇 Inbox 流程：选择或创建目标 Topic，放入一份 PDF，检查文件、目标及服务和处理说明，明确确认后开始入库。仅放入 Inbox 不触发远端解析或模型调用，刷新后仍保留待确认项目。

确认后的共享入库流程检查原件身份：已有相同文档时复用 Source／Parser Bundle，只补目标 Topic 关联；新文档才执行解析、规范化、元数据处理和 Bundle 校验，由 Core 发布唯一 Source。用户可直接查看原件、正文和引用图片，无需创建 Reading Plan，也不进入全文翻译、博客或阅读。

Bundle 发布与 Topic 关联分别报告。文档已入库但关联失败时，保留可访问的 Source，显示“目标专题关联待恢复”；续接只补关联。其他失败也从最后有效断点继续。取消立即关闭当前 attempt 的提交资格，已完成产物保留。所有正式提交都通过唯一 Core 写入入口，并校验版本、请求与写入方身份。

## User Stories

1. As a 读者, I want 选择已有 Topic 作为目标, so that 文档出现在我的专题视图中。
2. As a 读者, I want 在添加材料时创建最小 Topic, so that 新专题不依赖完整管理界面才能使用。
3. As a 读者, I want 将单篇 PDF 放入 Inbox, so that 我能先检查材料再决定处理。
4. As a 读者, I want 放入 Inbox 后不立即外发内容, so that 处理只发生在我确认的范围内。
5. As a 读者, I want 刷新后仍看见未确认项目, so that 我不必重新选择同一文件。
6. As a 读者, I want 在确认前看清文件、目标专题、服务、用途和处理范围, so that 我知道本次会执行什么。
7. As a 读者, I want 修改文件或处理范围后重新确认, so that 旧授权不会被用于不同任务。
8. As a 读者, I want 本阶段只处理入库, so that 上传不会自动生成博客、规划或翻译全文。
9. As a 读者, I want 入库状态反映真实业务进展, so that 模型说“已完成”不会误导我。
10. As a 读者, I want 成功后打开 PDF 原件, so that 我能核对来源。
11. As a 读者, I want 查看解析正文和可定位的图片引用, so that 后续阅读有可追溯材料。
12. As a 读者, I want 未知标题以外的出版信息等字段保持未知, so that 模型不替我编造证据。
13. As a 读者, I want 没有 Reading Plan 的文档也能入库和被查看, so that 精读是后续选择。
14. As a 读者, I want 文件改名后仍识别为相同原件, so that 我不会重复付出解析成本。
15. As a 读者, I want 同一 PDF 加入另一个 Topic 时复用已有 Bundle, so that 分类不会产生资产副本。
16. As a 读者, I want 新增 Topic 关联保留原有 Topic 关联, so that 一篇文档可以服务多个专题。
17. As a 读者, I want 重复点击确认或重放同一请求不重复发布, so that 网络和操作重试不会增加重复资产。
18. As a 读者, I want 相同标题但不同内容不被自动合并, so that 不同文档不会互相覆盖。
19. As a 读者, I want 看见“文档已入库”与“专题关联待恢复”的区别, so that 我能理解部分成功。
20. As a 读者, I want 专题关联失败后仍能从 Inbox 打开已入库文档, so that 已有成果不被隐藏。
21. As a 读者, I want 关联重试只补目标 Topic, so that 已成功解析的文档不再上传。
22. As a 读者, I want 远端解析等待超时后查询并续接原任务, so that 重试沿当前进展继续。
23. As a 读者, I want 应用重启后恢复有效断点, so that 进程退出不会迫使整个任务从头执行。
24. As a 读者, I want 暂时性网络错误获得有限自动续接, so that 短暂波动不要求我不断操作。
25. As a 读者, I want 自动续接两次仍失败时保留断点并提示手动重试, so that 重试成本和行为可控。
26. As a 读者, I want 认证或结果校验失败时看到明确错误, so that 系统不会反复执行无效请求。
27. As a 读者, I want 无法确认远端受理状态时看到“状态待核对”, so that 应用不会盲目重复上传。
28. As a 读者, I want 取消当前任务后阻止迟到结果发布, so that 停止操作确实影响业务提交。
29. As a 读者, I want 取消后保留已完成产物并能主动继续, so that 我不必放弃有效进展。
30. As a 读者, I want 版本冲突时保留候选结果并报告冲突, so that 当前资产不被旧结果覆盖。
31. As a 工作区拥有者, I want 第二个 Host 无法同时获得写入权, so that 本地资产不会被两个进程竞争修改。
32. As a 工作区拥有者, I want 凭据和私人旧资产与试验隔离, so that 验证新流程不改写现有阅读数据。
33. As a 后续宿主集成开发者, I want 通过同一 Application 调用入库, so that DSH 接入时不复制业务编排。
34. As a 验收者, I want 分别看到确定性测试、Host、浏览器与真实服务证据, so that 局部通过不会被误报为完整交付。

## Implementation Decisions

### 共用入口与职责

1. 以共享 Application 的单篇入库 Interface 作为唯一业务编排入口。它覆盖 Inbox 接收与查询、确认开始、查询进展、失败续接、取消和来源结果访问；这是一个业务 Module 的操作集合，不是每种操作另起一个流程系统。
2. 从当前 HostService 上传编排增量抽取所需行为。Host 负责本地上传、认证、HTTP／SSE 与会话装配，UI 负责展示和用户动作；均不自行决定解析后步骤或直接修改知识资产。
3. 复用 WorkspaceCore、SourceLibrary 的身份分配、Bundle 校验和文件持久化能力，按本切面需要迁入正常 Python 包。保留的旧包装只单向调用同一实现。新版入库不再走上传后规划／全文准备链路；旧阅读功能不在本阶段整体重写。
4. Parser 执行解析及来源表示转换，Runtime 只执行必要的受限 AI 子步骤；模型只交付候选结果，不能以自由 shell／patch 写入正式资产替代 Core 提交。当前允许普通文件工具的 Runtime 配置不能直接视为达标。
5. Parser／Runtime 通过注入的最小 Interface 接入 Application。复用现有参考实现，不建设通用 Agent harness、通用工作流引擎或跨 Runtime 完整会话迁移。业务 Run 不等同于 Runtime turn。
6. 本阶段统一使用 `article-parser` 作为解析 Skill，重写其方法并迁入可复用的 PDF 实现，保留既有 HTML 能力。覆盖 Parse／Normalize／Metadata／Compose／Export，删除旧 `paper-parser` Skill 及废弃调用入口，不留旧名称兼容壳。Host 路由、Core 的 Bundle 校验、解析产物标识、博客消费检查、文档和测试同步更新，不能只改目录名。方法只有一个版本化编辑源，安装副本不另行编辑；新版入库不附带规划或全文准备。旧私人 Bundle 的历史 provenance 不在本阶段批量改写；已有阅读资产保持原样，不能为清除历史字符串迁移数据。

### 确认与 Inbox

7. Inbox 保存本地选择、目标和业务状态，但不是已注册 Reading Source。输入格式和基本有效性可以本地检查；未确认时对 Parser 和 Runtime 的外发调用必须为零。
8. 确认绑定具体原件、目标、参考服务／配置和明确处理范围，保留可校验的确认依据。输入或范围变化不得复用旧确认；不能只依赖提示词说“已经授权”。
9. 阶段 1 的确认范围仅为单篇入库。未来完整产品的“解析＋博客”一次确认不意味着本阶段应提前执行博客。问答、进入精读和 Continue Reading 分别触发。
10. 持久化状态必须能区分待确认、处理中、需手动重试、状态待核对、取消、版本冲突，以及文档发布和 Topic 关联结果。UI 展示面向用户的状态，不要求展示内部 Run／attempt ID，也不以模型文字推断成功。

### 身份、关系和发布

11. 同一 PDF 内容复用相同 Source，文件名与 Topic 不参与原件身份。Source ID、Source Identity、解析任务 ID、Bundle 版本及目录显示名称分别处理；同标题不同原件按现有稳定命名／消歧规则注册，不自动推断作品版本关系。
12. 所有来源资产归统一 Source Library，每个 Source 的 Bundle 只保存一份。Topic 的有序 Source ID 集合是关系的唯一权威；详情页 Topic 标签和反向查询由它派生，不在论文或 Bundle metadata 中重复维护可修改关系，不新增持久化反向索引或数据库。
13. 首阶段提供选择与最小创建 Topic 的能力；重复文档只增加缺失关联，原有成员关系和顺序保留。重复添加同一成员不产生重复项。新建 Topic 不允许以覆盖已有同名专题资料的方式实现。
14. 合法 Bundle 至少保留字节一致原件、非空正文、可解析最小元数据、能访问的引用图片及结构验证结果。未知出版信息不编造，正文引用不得指向缺失或越界资源。
15. 无效候选不得注册为正式 Source。Bundle 发布后文档入库成功，不要求 Plan、全文译文或博客；新 Source 不开始阅读、不产生 Plan／Chunk。复用旧 Source 不改变其既有 Plan、Cursor、Records 或 Notes。
16. 文档发布与目标 Topic 关联分别具有结果。关联失败保留有效 Source，Inbox 可访问来源并显示关联待恢复；整体 Inbox 任务只有完成所确认的目标关联才算完整结束。Topic 视图只列出已经关联的 Source。
17. 若发生提交成功但响应丢失，恢复必须依据 Core 的持久结果识别已完成提交，不能重新解析、再次发布或重复关联。

### 最小持久化与续接

18. 新增仅供入库所需的版本、业务 Run／Step／attempt、请求与写入方信息。已有 Topic／Source 身份规则继续生效；不在此冻结全产品 schema，也不迁移私人旧工作区。
19. Run 标识同一次业务任务；Step 划分可恢复进展；attempt 标识步骤的一次执行，绑定服务／模型、方法版本和输入版本。查询或轮询同一远端任务不算重新执行步骤。
20. 实施至少能恢复这些业务断点：已确认输入；已知远端任务引用；可复用解析结果；待校验／发布候选；已发布 Source；待完成 Topic 关联。具体内部步骤命名可调整，不能丢失上述恢复能力。
21. 一旦取得远端任务引用就将非秘密恢复信息持久化，不等整个上传或解析成功后才记录。签名 URL、token 和原生私密会话内容不进入业务断点。受理结果未知时先查询；无法确定原任务则停在状态待核对，不自动提交第二份。
22. 失败续接保留已提交产物及有效断点，只重新执行没有有效结果的未完成部分。获取已有远端结果、重新校验本地候选、补 Topic 关联分别复用各自已有进展，不统一降级成“重新上传”。
23. 同一输入、服务和授权范围内的手动重试沿用确认；改变输入、服务或范围重新确认。暂时性网络错误最多自动续接两次，之后等待手动动作；正常进度轮询不消耗重新执行次数。认证和校验失败直接报告，不能伪装为可无限重试的网络失败。
24. 取消先持久化当前 attempt 的提交禁令，再请求外部服务停止。若服务仍在运行，显示实际状态；取消不是撤回已提交产物，也不承诺撤销远端计费。再次明确继续创建新 attempt，从最后有效断点开始，旧 attempt 迟到结果不得提交。

### 唯一写入与冲突

25. Core 正式提交要求预期版本、请求 ID 和当前有效写入方身份。幂等判定与提交结果须可跨进程重启恢复，不能仅使用浏览器标记或 Host 内存去重。同请求重放返回已有结果，不重复产生业务副作用。
26. 版本已变化时报告冲突并保留候选供后续处理，不能静默覆盖现有资产，也不能把未发布候选展示为新正式 Bundle。Source 发布和 Topic 关系更新各自检查相关状态，改 Topic 不应重写解析内容。
27. 同一工作区仅一个有效写入方；第二个独立 Host 不能获取并发写入权。复用现有单写者与原子文件操作机制并验证进程重启边界，不能仅靠单个进程内的锁。等待 Parser／Runtime 时不持有长期资产提交临界区；工作区独占所有权与短期提交锁分别处理。
28. 方法、业务输入和展示不得暴露凭据；Parser／Runtime 所需凭据留在对应适配器的服务端环境。未配置或不具备任务所需能力时明确阻止该任务，不静默改用另一服务或 fixture。

## Testing Decisions

### 最高层测试边界

主边界为共享 Application 的单篇入库 Interface，优先复用现有 HostService 对外业务动作的语义，向共用层收敛。测试调用用户动作并读取业务状态，使用真实 Core、真实隔离持久目录与可控 Parser／Runtime；不 mock Core 成功来证明提交成功，不以内部调用顺序、私有字段或提示词文本作为主要断言。

可控适配器只负责产生外部成功、超时、受理不明、无效结果和迟到响应。主测试验证最终资产、可访问结果、持久断点、幂等行为，以及是否发生额外远端提交。进程重启和第二写入者案例使用真实持久状态／进程边界，不只重新构造 UI。

少量独立 Host 与浏览器验收证明真实 UI 动作连接该 Application，覆盖上传、确认、刷新和结果访问，不在 UI 再复制整套业务状态测试。Parser 协议与不可信产物校验沿用必要的低层边界测试；新增低层测试必须有主边界无法清楚验证的理由。

### 必须覆盖的行为

| 编号 | 场景 | 可观察结果 |
| --- | --- | --- |
| T01 | 放入 PDF 后刷新、重启 | Inbox 仍待确认，Parser／Runtime 外发次数为零，无正式 Source |
| T02 | 修改原件或确认范围后提交旧确认 | 拒绝旧确认，不外发 |
| T03 | 授权单篇正常入库 | 合法 Source／Bundle、目标关联和来源出口存在，无 Plan／翻译／博客 |
| T04 | Runtime 宣称完成但没有有效候选 | 不发布、不显示业务成功 |
| T05 | 图片缺失、非法路径、结构无效或原件不一致 | 校验失败，无新正式资产 |
| T06 | 重命名相同 PDF 后加入另一 Topic | Source 和 Bundle 唯一，原有关联保留，零新解析调用 |
| T07 | 相同请求／确认重复提交及重启后重放 | 返回已有结果，无重复发布或重复 Topic 成员 |
| T08 | 相同标题但不同 PDF | 不误合并，不覆盖既有 Source |
| T09 | Bundle 发布成功、Topic 关联失败 | 文档仍可查看；关联待恢复，续接只补关联 |
| T10 | 解析超时且远端任务号已知 | 查询／续接原任务，无新上传 |
| T11 | 远端是否受理未知 | 查询后仍无法定位则状态待核对，不自动第二次提交 |
| T12 | 已取得任务引用后进程退出 | 重启后保留引用并续接，不丢回未开始状态 |
| T13 | 本地有效解析结果已存在，校验／发布未完成 | 复用有效结果，不重新调用解析 |
| T14 | Core 已提交但调用方未收到结果 | 恢复识别已提交结果，不重复副作用 |
| T15 | 暂时性网络错误持续发生 | 最多两次自动续接，随后等待手动重试，断点仍在 |
| T16 | 认证失败或校验失败 | 直接给出对应错误，不走无限或网络自动重试 |
| T17 | 取消后 Runtime 仍返回候选 | 原 attempt 永久不可提交，原有合法产物保留 |
| T18 | 取消后主动继续 | 新 attempt 从有效断点执行；旧 attempt 的结果仍被拒绝 |
| T19 | 候选基于旧版本，提交前资产已更新 | 冲突可见，候选保留，当前资产未被覆盖 |
| T20 | 第二 Host 或无效写入方尝试提交 | 写入被拒绝，工作区保持一致 |
| T21 | 重复添加带历史阅读资产的 Source | Plan、Cursor、Records、Notes 不被改写 |
| T22 | 阶段 1 新入口执行后检查后续步骤 | 没有旧上传规划／全文准备触发；无额外 Runtime 循环 |
| T23 | 未认证、越界资源请求或凭据出现在远端错误中 | Host 拒绝越权访问，错误及持久化结果不泄漏凭据 |
| T24 | 浏览器完整操作与刷新恢复 | 状态来源一致，已入库／关联待恢复清楚区分，原件正文图片可访问 |

### 现有测试先例与更新方式

- PaperParserTests 已有合法注册、无效 Bundle、超时按 batch 恢复、原件复用、图片引用和凭据处理案例；复用其外部适配器替身模式，将新版业务验收提升至 Application。
- SourceLibraryTopicTests 与 FoundationTests 已有单 Source 多 Topic、命名消歧和缺失图片案例，可作为现有资产规则依据。

### 真实证据与完成门槛

1. 确定性层：通过上述主边界场景，包含持久化、故障注入与进程写入保护。
2. Host 层：证明独立 Host 实际调用同一 Application，认证、资源出口与状态恢复有效。
3. 浏览器层：完成单篇放入、确认、查看原文、刷新和可控失败恢复；新流程没有触发旧全文准备。
4. 真实 Parser 层：使用已授权参考 PDF 验证新链路的真实解析；已有阶段 0 Parser 结果只能证明旧 Parser 可用，不能替代新 Host 流程验收。验证重复文档路径时必须复用产物，不为凑证据重新解析同一已入库 Source。
5. 真实 Runtime 层：在隔离环境验证参考 Codex 对当前入库所需 AI 步骤的真实认证、模型可用性、工具约束、结果校验与取消；涉及图像时须验证图像能力。本地版本或登录状态不等于这一层通过。
6. 内容层：抽查参考 PDF 的核心图表、公式和阅读顺序，结构通过不代表语义质量通过。博客质量属于后续阶段。
7. 基线层：运行与改动相关的 Python、UI 测试和必要构建，结束时刷新全套失败清单，分别记录通过、失败、未测及历史证据。

缺少真实 Runtime 能力或新写入约束时，允许完成确定性实现与故障测试，但对应真实任务不得被标为可用，阶段 1 不得宣布完整验收通过。

- 博客生成、文章长文／HTML 导出、整篇问答、Source 级独立备注、精读规划、按需翻译与 Continue Reading 改造。
- 批量 Inbox、HTML／Markdown 新入库能力验收，以及完整 Topic CRUD、删除和资料管理界面。统一 Parser 时保留既有 HTML 能力并做必要回归；不把新双格式完整产品验收提前到本阶段。
- 主动重新解析的产品入口及完整版本浏览；本阶段保留显式新版本和预期版本契约，不把重复添加当作重新解析。
- DSH 原生接入、其他 Runtime、WorkBuddy／CodeBuddy 接入、运行中跨 Runtime 热切换。
- 全仓目录搬迁、私人旧 schema 转换、旧工作区迁移和备份演练实施。
- 新知识数据库、持久化反向索引、重复 Topic metadata、通用工作流引擎、完整事件存储或通用 harness。
- 多用户生产部署、网络盘并发、两个独立 Host 同时写同一工作区。
- 改写 v0.1 或补齐其缺失章节；v0.2 是独立需求依据。
