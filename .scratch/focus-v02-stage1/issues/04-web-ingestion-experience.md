# 04: 接入独立网页的最小入库体验

What to build: 在已稳定的后端上提供最小 Inbox、确认、进度、Topic 展示和来源查看，让用户在网页完成单篇入库、重复添加和失败续接，前端不编排业务。

Blocked by: 03 — 完成后端续接与真实运行验证

Status: resolved

- [x] 根据已完成的 Application 状态和操作，接入 Topic 选择／最小创建、单 PDF 暂存、处理说明和明确确认；前端不直接驱动 Parser／Runtime 或写知识资产。
- [x] 展示待确认、处理进展、可继续的失败、取消和状态待核对；区分文档已入库与专题关联待恢复，不向普通用户堆内部执行标识。
- [x] 按 Topic 展示来源；同一文档在多个专题引用同一资产，详情 Topic 标签来自唯一关系。无 Plan 来源可打开 PDF 原件、正文和引用图片；关联失败仍能从 Inbox 访问。
- [x] 刷新／重新连接取权威状态；重试、取消、再次继续调用后端已有动作，不维护第二套业务状态机、不把旧上传规划流程接回来。
- [x] 少量 Host／浏览器场景验证成功入库、跨 Topic 重复添加、刷新恢复及关联失败续接；复用后端证明，不在浏览器重复完整故障矩阵。认证和资源访问约束实际接通。
- [x] 完成一次必要整体回归及 UI 类型／构建检查，刷新全套失败清单。按用户决定删除已失效且无关的测试，保留有效失败并说明；汇总确定性、Host、浏览器、真实服务结果与剩余限制。

Verification: 独立网页版演示用户闭环，使用隔离数据；已有合法 Bundle 的重复添加不得触发新解析。不扩展完整 Topic CRUD、博客、精读、批量或新格式产品验收。

Spec coverage: T24、T23 的 Host／资源接入与各后端状态的必要 UI 投影；阶段 1 综合结果与开发结束基线刷新。

## Answer

ReaderHost 和 HTTP 现只把单 PDF 暂存到持久 Inbox；确认和处理是两个独立动作，后台线程只调用共享 Application。网页投影权威状态并轮询处理中项目，提供续接、取消、刷新，以及文档／专题分别完成的状态；所有可恢复状态也提供显式重新确认，配置漂移不会形成死路。Source 卡和 Inbox 都从 Core 的唯一 Topic 关系显示标签，并经同一认证边界访问原件、正文和相对 `images/` 资源。隔离的真实 Workspace 浏览器演示确认“暂存不外发”、刷新恢复、已完成 Inbox 与无 Plan Source 资源入口。旧 `/library/sources` 上传规划入口及其 5 项失效测试已删除；保留的 Source ID 测试改为验证当前打开／准备路径。审查后补强四方原件一致性、崩溃候选精确复用、配置绑定与重新确认、原子状态转换、全链路取消竞态和取消态输入保护、全 Step 中断恢复、Host writer identity、既有阅读位置保持与畸形 Inbox 响应拒绝。全量 Python 138 项、UI 42 项通过，UI 类型检查、生产构建与 Python compileall 通过；构建只有既有单块大于 500 kB 的 Vite 警告。
