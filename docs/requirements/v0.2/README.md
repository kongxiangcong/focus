# v0.2 分阶段需求索引

日期：2026-09-21。状态：阶段 0 grill 已完成、实测验收部分完成；阶段 1 已按确认 spec 完成并留下分层验收证据；其他阶段待 grill。本目录是需求索引，不是整个产品已完成声明。

需求权威是 [FOCUS v0.2 总计划](../../../FOCUS_Shared_Workflow_MultiHost_Plan_v0.2.md)。本目录只细分交付顺序、范围和验收出口；不重新定义产品。总计划的 P0–P5 与本目录的阶段编号不是一一对应关系。

## 划分依据

当前基线已经有 Source Library、Topic、PDF/HTML/Markdown 上传、ReaderHost、Codex 适配和全文阅读准备。主要工作是拆开原有“上传→规划→全文准备”耦合，补齐 Inbox、共享 Application、博客编排和独立备注。详细证据及 ADR 冲突见 [当前基线](baseline.md)。

沿用建议中的 0–6 主线，作三项调整：

- 阶段 1 内完成支撑单篇入库的最小共享层，后续按功能增量抽取；阶段 0 不冻结全项目 schema，也不整体迁目录。
- 阶段 2 附近加入 DSH 早期探针。其目标是验证同一 Application 和受限 AI 步骤，及时发现宿主契约问题；不能把首次 DSH 接入推迟到阶段 6。
- 阶段 5 拆成四个需求单元；另保留总计划 P5 的 Runtime 扩展阶段 7，按实际优先级逐个接入，不阻塞独立版发布。

## 跨阶段共同约束

继承总计划 §1–5、§7–8：Core 是唯一资产写入权威，Application 是唯一业务编排，Methods 只有一个编辑源；UI／Host／Runtime 分别装配和适配。Bundle、Blog、用户 Reading Note、Plan 是不同资产；Source ID、解析 ID、Bundle 版本和路径名称不能混用。

从阶段 1 首次外发与写入起，就必须落实确认、版本校验、请求幂等、写入方身份、独占写入、取消后拒绝迟到结果、断点恢复和凭据隔离。后续阶段扩展这些规则的适用对象，而非等发布时补安全底座。Runtime 结束与 Core 提交成功分开报告。问答、理解确认与 Continue Reading 的授权分开。

阶段 0 明确首批契约；阶段 1 随入库引入共用 Parser／Runtime 边界和方法资源；阶段 2–4 按功能扩展，2D 验证跨进程可用性。目标目录分批迁入，薄包装只允许单向调用同一实现，不形成长期双业务路径。代码布局、字段结构与协议细节留给 spec。

所有出口分别记录：代码／fixture、Host 集成、浏览器、真实 Parser／Runtime。真实输出还需检查方法深度、图表理解、引用和纠错质量；不要求不同模型逐字相同。没有真实证据的能力标为待验收。

## 后续使用方式

每轮只取一个阶段文件，同时读取本索引、基线、总计划对应章节以及已完成的前置阶段结果。

1. 用 `grill-with-docs` 讨论该阶段的待决问题；按其 `grilling`／`domain-modeling` 流程收敛决策和需要替代的 ADR。后续阶段仅作边界，不提前设计全部实现。
2. 用 `to-spec` 将已收敛讨论整理到 `.scratch/focus-v02-<stage>/spec.md`，确认最高层可用测试边界。
3. 用 `to-tickets` 拆纵向交付、确认粒度与真实阻塞边，按仓库规则一票一文件放入同目录的 `issues/`。

本目录不标记 `ready-for-agent`。按用户显式调用生成的 spec／tickets 放入本地 tracker；当前 [阶段 1 spec](../../../.scratch/focus-v02-stage1/spec.md) 及用户批准的 [4 张实施票](../../../.scratch/focus-v02-stage1/README.md) 已依次实施，综合证据见 [阶段 1 验收记录](stage-1-acceptance.md)。下一轮重新核对代码基线，避免把这里的现状快照当成永久事实。`.scratch/` 默认受 Git 忽略；本阶段 spec、任务索引和 4 张票已显式纳入版本管理，试验数据保持本地。
