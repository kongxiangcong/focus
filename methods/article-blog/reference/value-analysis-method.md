# 论文架构价值分析：指导手册

## 1. 定位与输出

本手册指导“论文架构价值分析”技能，从 NPU 硬件架构、架构建模与编译的视角，讲清一项工作解决的问题、系统边界、核心机制、证据和可借鉴内容。它不是摘要、审稿打分表，也不是完整复现流程；可独立使用，不要求加载博客手册。

输出 Markdown（`.md`）。标题下简要标明论文来源、版本和本次核查范围。正文固定采用以下顺序：

**研究问题 → 输入输出 → 模块拆解 → 一个运行例子 → 贡献与边界。**

先让读者理解工作怎样运转，再判断贡献。实现审查细节和补充资料按需附后，不打断首次理解的主线。内部核查项按论文实际内容选择，不要求逐项出现在正文。

## 2. 分类：以核心贡献为主，不以工具名称归类

本手册按研究目标区分以下方向。系统可以同时包含多个角色；论文主方向由新增设计、核心主张及其验证对象决定，不能只看标题、关键词、章节篇幅或工具名称。

| 方向 | 重点识别的贡献 | 需要区分的支撑工作 |
| --- | --- | --- |
| **硬件架构** | 计算、存储、互连、控制、同步或指令执行机制，以及面向特定模型或负载族的硬件组织与软硬件分工 | 编译器负责映射与生成执行任务，仿真器和 DSE 可用于实现或验证架构，但不因此成为论文主方向 |
| **设计空间探索（DSE）** | 设计变量、合法空间、优化目标、候选生成与搜索选择；可联合探索硬件与映射 | 评估器给候选估价，编译模块构造候选；不能把评估一个方案等同于搜索方案 |
| **编译器与编译优化** | 将计算语义转换为目标相关表示、映射、存储方案、调度或可执行产物的机制 | 使用搜索或成本模型不自动改归 DSE；只贡献一个编译阶段，也不要求具备整套编译器 |
| **仿真器** | 按明确的功能、状态、资源或时序规则推演执行过程的机制 | 仿真器可能成为 DSE 的评估器；是否逐周期、是否输出周期数，不能代替建模范围与精度核查 |
| **性能建模与评估器** | 从工作负载和执行方案得到延迟、能耗、流量等估计的方法、参数与验证 | 估价方法与搜索算法分开识别；分析模型、仿真或实测可以承担评估角色 |

分类应表达为：**主方向＋核心贡献模块＋支撑角色＋判断依据**。允许联合主方向或暂不能确认，不强行单选；初读形成假设，完成机制与证据核查后复核。

### 2.1 硬件架构的边界

面向一个模型定制、面向一类模型优化、面向多类推理任务的可编程架构，都可属于硬件架构研究。需要查明哪些特征被固化，哪些可配置或可编程，适用范围由什么证据支撑。

提出新的硬件组织，与给已有硬件建立参数化表示，不是同一项贡献。后一项应进一步判断重点是表示／建模、编译适配还是探索。反之，架构只通过模型或仿真评估，也不因此失去架构类别；验证方式单独记录。

“架构为主、编译为辅”描述的是论文贡献重心，不表示软件不重要。必须说明硬件提供什么机制，编译器和运行时承担什么决策。编译侧也提出明确新方法且有对应论证或联合验证时，可以列为并列贡献；不要求协同设计的各部分都能独立验证，但不能虚构单项收益。

分类参照：M100 [1] 的第三、四节展开硬件设计，第五节介绍编译与运行时。本手册将其作为“硬件架构为主、编译与运行时协同支撑”的例子，围绕数据流执行、存储／互连和同步理解其设计；其范围覆盖多类推理场景，不应限定为单模型固定流水线。

## 3. 内部分析流程

### 3.1 确认材料，并在技术细读前查找实现

确认论文题目、版本、正文与补充材料，以用户提供的版本为分析对象。解析文本中的关键公式、图表或疑似错误需回看原文；未提取到不等于论文未提供。新版论文或代码与分析版本不同时，明确差异。

先检查论文内部的代码、项目页和 artifact 链接，再查作者或机构发布的官方仓库与材料。第三方复现单独标明，不用它补全作者未公开的实现。访问不了或未找到实现，应记录检索范围和缺口，不能直接断言未开源。

架构论文同时查找可获得的 RTL／HLS、仿真器、硬件配置、编译与运行时、评估脚本等；只核查实际公开且与贡献相关的部分，不要求每项都有。

### 3.2 联合论文与实现，建立证据清单

先确定系统边界与模块，再为核心主张记录对应的论文位置、机制、实验和实现位置。源码可访问时，必须沿相关入口、配置、关键模块和结果生成路径核查，不能止于 README 或目录浏览，也不要求逐文件审计整个仓库。

对影响结论的主张，尽量建立：

**论文主张 → 实现位置 → 实验配置／脚本 → 支持的结果。**

区分作者陈述、论文展示的证据、源码静态核查、实际运行结果和本文推断。源码可执行不等于已经运行；运行一个示例不等于复现论文实验。默认以阅读和静态核查为主，不自动开展部署、完整复现或新实验。

### 3.3 推演核心路径，再形成判断

选择能暴露关键机制的小规模案例，追踪输入、中间状态和输出，并核对模块之间的接口。发现缺失环节时明确标记，不用通用架构常识补成作者实现。

回到实验，检查证据是否支持所识别的贡献与适用范围，最后复核主方向。材料不足时给出有边界的分析，不将猜测升级为确定结论。

## 4. 正文：固定五段主线

### 4.1 研究问题

用直接的语言说明研究对象、场景、瓶颈和约束，以及现有方法为何不足。不能以“提高效率”“优化性能”结束问题定义。背景只补到理解该问题所需的程度。

在本节给出主方向与支撑角色，并说明依据。架构论文优先回答：目标负载有什么计算、访问或控制特征，为什么值得改变硬件组织，而不只是优化已有平台上的实现。

### 4.2 输入输出

先说分析对象的边界：哪些已知条件来自用户或环境，哪些由该工作决定，最终产生什么，由谁继续使用。

对 DSE、编译器、仿真器和评估器，说明实际输入格式或内容、可选择变量与输出产物，区分性能数字、映射方案、调度、中间表示和目标可执行产物。

对硬件架构，分开说明**设计层**与**执行层**：设计层从负载需求和资源约束出发，形成硬件组织与软硬件接口；执行层接收何种任务、指令和数据，数据从哪里进入、由哪些单元处理、结果存到哪里。不要给硬件论文强套软件工具的文件输入输出格式。

始终区分“研究软件如何运行”和“被研究的工作负载如何执行”。例如，在主机上运行仿真程序，不等于工作负载已经在目标芯片上执行。

### 4.3 模块拆解

先给出整体关系，再单独展开核心模块。总表只用于导航：

| 模块 | 拿到什么 | 做什么 | 产出什么 |
| --- | --- | --- | --- |
| 按论文的真实模块填写 | 数据、状态、请求或表示 | 关键动作与决策 | 数据、响应、状态变化或产物 |

各关键模块围绕设计动机、内部机制、必要技术对象和代价展开。公式解释变量与用途，算法说明决策规则，硬件模块说明数据与控制如何交互。图解要解释连接、箭头和存储关系，而非只重复模块名。

硬件论文先讲总体组织和核心硬件路径，再解释使其运行的软件分工；编译论文先讲表示与转换；其他方向按实际主路径组织。不要把物理模块、编译阶段和搜索步骤混成同一层级。

贡献判断集中放在末节；源码文件路径和核查细节按需移入附录。没有源码支持时，不把论文概念名当作真实函数或文件名。

### 4.4 一个运行例子

优先使用论文或官方实现中的案例；没有合适案例时，构造保留核心机制的教学例子，并明确简化和假设。标明案例属于论文示例、源码示例、教学推演还是本次实际运行。

例子不能只串联模块名称，必须展示关键中间变化。按主方向选择路径：

| 主方向 | 例子应追踪的路径 |
| --- | --- |
| 硬件架构 | 输入所在存储 → 搬运／访问 → 计算与中间数据 → 依赖满足和缓冲回收 → 输出位置 |
| DSE | 一个候选如何产生、通过合法性检查、获得估价，以及怎样影响下一步搜索或选择 |
| 编译器 | 一段计算如何经过关键表示与决策，落实为该工作实际支持的目标产物 |
| 仿真器 | 一项操作或请求怎样改变状态、等待资源、推进时间并计入结果 |
| 性能建模 | 一组输入与方案怎样转化为成本项，如何处理重叠或瓶颈并得到估计 |

联合型工作讲清必要的衔接即可，不要求为每个支撑角色另做例子。论文没有给出的地址、周期和仲裁行为不得伪造；示意数值不能冒充作者数据。

### 4.5 贡献与边界

在读者理解机制后，逐项说明：相对已有基座新增了什么，什么证据支持它，成立需要哪些前提，尚未覆盖什么。区分作者宣称的贡献与本次核查能够确认的贡献。

实验解读保留比较对象、负载规模、精度、资源配置、指标定义与测量范围。局部算子收益不能代替端到端收益；最佳结果不能代替普遍表现；搜索或仿真软件运行更快不能写成目标硬件更快。

架构与编译共同优化后的系统结果，不自动证明某一硬件模块的独立收益。没有对应消融或控制变量证据时，只讨论可支持的联合效果与可能解释。因果解释、迁移预测和教学推导须与已验证结果分开。

最后落到架构工作价值：值得借鉴的是硬件机制、表示、优化方法、模型还是软件基座；迁移需要哪些条件；哪些问题仍需验证。研究方法强与工程基座适合改造分别判断，不用单一分数替代分析，不强行制造研究空白。

## 5. 分方向核查重点

以下问题用于选取分析重点，不是正文必须填满的表单。未涉及但影响主结论的环节要指出，其余不堆砌“不适用”。

### 5.1 硬件架构

沿 **负载特征 → 瓶颈 → 硬件选择 → 执行过程 → 验证与代价** 检查。

**负载与专用化。** 面向哪个模型、算子组合或负载族？数据形状、复用、精度、稀疏性、动态行为与主要瓶颈是什么？哪些假设固化到硬件，换模型或规模后哪些能力仍成立？算法变化与硬件变化的影响能否区分？

**计算与数据路径。** 计算单元怎样组织，数据和部分结果放在哪里，容量、端口与带宽能否支撑并发？数据怎样在本地存储、共享存储、片外存储和不同核之间移动？互连、DMA、bank 竞争或广播哪些有实际机制，哪些只作理想假设？参数应连接到设计取舍，不止列规格。

**控制、同步与执行粒度。** 任务怎样进入硬件，何时可执行，由谁检查依赖？消费者怎样获知数据可读，生产者怎样知道缓冲可复用？分清编译期确定的决策、运行时重新作出的决策，以及只等待就绪条件再推进的执行。按依赖自定时推进不应自动称为动态调度；静态计划也不必意味着全系统按固定周期执行。

**软硬件契约。** 硬件保证什么，编译器、运行时与固件分别负责什么？检查分块、放置、地址生成、指令粒度、同步表达和异常／不规则路径中与核心贡献相关的接口。软件承担更多工作时，说明换来的硬件简化及软件成本，而非只写“软硬件协同”。

**代价与可扩展性。** 性能收益付出哪些面积、功耗、存储、互连、控制或编译成本？瓶颈是否转移？更大模型、更多核或不同负载下的适用性，是实验结果还是推测？没有公开数据的成本不能自行估成已知事实。

### 5.2 DSE

检查设计变量、合法性约束、优化目标、候选生成与搜索算法；区分硬件空间、映射空间和联合空间。

检查评估器来源、每个候选的评估成本、搜索预算及与基线比较的公平性。分别判断估价是否准确、搜索是否有效、选出的方案是否能在所声称的目标范围内实现。找到低估成本的候选不等于找到更好的实际方案。

### 5.3 编译器与编译优化

检查输入语义、关键中间表示、转换与决策，以及硬件约束如何进入合法性判断。按论文涉及范围核查分块、放置、生命周期、调度、通信和同步。

明确实现终点：停在映射或调度，还是继续生成地址、指令／描述符及可被后端消费的程序？检查正确性与性能验证覆盖范围。模块级创新不必实现全部阶段，但不能把未实现的后半段描述成已有能力。

### 5.4 仿真器

检查驱动输入、被模拟的组件与状态，以及功能和时序分别覆盖什么。对于重要的访问或操作，说明它经过哪些队列、控制器、存储或计算模型；哪里显式推演，哪里用固定延迟、统计或分析结果替代。

检查资源竞争、背压、同步及模型粒度。声明的“周期精确”不能代替验证依据：还需看对照对象、覆盖范围、误差与仿真速度。不因未模拟数据值就直接否定时序仿真，也不因实现部分细节就推断完整系统精度。

### 5.5 性能建模与评估器

检查成本项、公式、参数来源及标定方式，说明计算与通信如何组合，复用、重叠和竞争怎样处理。

检查误差口径、验证负载及配置范围，是否使用独立数据验证。估计平均误差小、候选排序可靠、跨硬件或跨负载泛化，是不同结论；分别说明证据支持到哪里。

## 6. 通用证据边界与表达

**验证方式与研究方向分开。** 分别记录工作负载的真实性、目标硬件形态、结果获得方式和验证覆盖。真实模型可以运行在建模硬件上；芯片实测、FPGA 原型、RTL 仿真、综合估计、事件／周期仿真与分析模型并非同一种证据。混合评估按指标注明来源，不用一个“真实／不真实”标签概括。

**来源要能定位。** 关键机制、数值和判断链接到论文章节、图表或实现位置。代码尽量标明核查版本与文件／函数；未获得版本信息时说明，不编造 commit、行号或运行记录。论文与实现不一致时并列说明，不悄悄选一方补全另一方。

**把材料不足写准确。** 区分没有访问权限、未找到公开材料、材料缺失、代码未覆盖和本次未运行。记录它们对结论的具体影响，不把未公开实现直接当作研究无价值，也不把读过论文说成实现已验证。

**保持阅读主线。** 首次解释关键术语，随后保持一致；每个核心模块单独讲清，少用缩写串与宽表。公式、原图或伪代码按机制需要选用，无数量配额。可用原图时优先核对和解读，自绘示意明确标识，不以概念图冒充真实硬件连线。

## 7. 交付检查

- 五段正文是否按约定顺序，读者能否先理解机制再看到评价？
- 主方向是否由贡献和证据决定，硬件设计与辅助编译、搜索、仿真是否区分？
- 输入输出和模块边界是否清楚，运行例子是否展示了真实中间变化？
- 有可访问官方实现时是否完成核心路径核查，并如实标明核查层级？
- 性能数字是否保留条件，联合效果、独立贡献和推测是否分开？
- 是否讲清可借鉴内容与迁移条件，没有评分替代论证或为凑数制造缺口？
